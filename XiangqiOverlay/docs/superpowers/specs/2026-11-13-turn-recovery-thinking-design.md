# 快速走子后的回合恢复与思考稳定性设计

日期：2026-11-13

## 背景与证据

用户反馈 JJ 象棋对局中会突然停在“等待对手走棋”，并希望优化引擎思考。新截图显示：游戏里的黑卒已经落到 `(2,6)`，软件小棋盘也显示了该黑卒，但当前行棋方和结果区域仍表现为黑方/等待对手。

离线诊断得到以下事实：

- 对合并截图直接自动校准会向左偏一格，不能拿该结果代替用户运行时的校准。
- 使用截图中的真实棋盘四角后，原始视觉能看到黑卒落点；从上一盘面重建 `(2,5) -> (2,6)` 时，现有单步推导和 `ConfirmedBoardUpdater` 都能通过，下一方应为红方。
- 因静态截图不包含运行时的上一已确认盘面、校准和引擎输出顺序，不能声称它已经复现完整卡住链路。

代码审查确认了以下独立缺陷：

1. `UciEngine` 的 `info` 和 `bestmove` 没有绑定发起搜索的 FEN。
2. `AnalysisManager` 收到结果后用“当前盘面 FEN”覆盖结果 FEN；快速连续提交时，旧搜索结果因此会被伪装成新盘面的结果。
3. `UciEngine.ParseInfoLine` 在没有 PV 时把 `currmove` 当作推荐；它只是引擎正在尝试的走法，不是最佳着。
4. `MainWindow.OnBoardRead` 只更新棋盘，不立即刷新“等待对手/正在思考”提示；旧提示可一直保留到下一次引擎输出。
5. 默认搜索只有深度 24，没有时间上限；推荐可能在较长时间内持续跳动。

这些缺陷能够解释快速走子时的状态污染和陈旧提示，但仍需通过确定性回归验证修复，不能用调低搜索深度代替状态修复。

## 目标

- 每个引擎结果都保留其真实搜索盘面；旧盘面的结果不得进入当前盘面的 UI 或“预期走法”通道。
- 新搜索请求到来时，先结束旧搜索，再启动最新请求；连续变化只保留最新待搜索盘面。
- 只把带 PV 的 `info` 和 `bestmove` 作为推荐，不再使用 `currmove` 伪装推荐。
- 已确认盘面提交后立即刷新回合提示，不等待引擎输出。
- 默认采用用户选择的“优先棋力”策略：最长 4 秒，深度上限 30；用户可在界面调整时间。
- 为真实黑卒走子、搜索会话切换、旧结果过滤和推荐解析建立回归。

## 非目标

- 不自动点击、不自动落子、不读取目标进程内存。
- 不重写视觉识别器或象棋规则。
- 不在本阶段接入天天象棋或 QQ/欢乐象棋。
- 不承诺仅凭单张截图证明所有运行时卡住原因均已消失；若仍存在拒绝提交，界面必须显示具体原因。

## 方案比较

### A. 只调整深度与提示

改动最小，但旧引擎结果仍会串台，不能解决快速走子时的核心竞争。

### B. 搜索会话序列化 + FEN 真值 + 回合提示刷新（采用）

保留现有进程通信和主控制器，在 `UciEngine` 内增加当前/待处理搜索会话，在 `AnalysisManager` 统一丢弃旧 FEN 结果，并由 UI 在盘面提交时立即更新提示。改动集中，可分别测试。

### C. 重写引擎调度与识别状态机

可一次性重新划分所有职责，但范围大、回归风险高，当前已有安全提交组件，没有必要重写。

## 组件设计

### 1. 搜索会话协调器

在 Engine 层增加纯 C# 的搜索会话协调器，供 `UciEngine` 使用并供 LogicTest 直接验证。

每个搜索请求包含：递增会话号、FEN、深度、节点数、思考时间和实际 `go` 命令参数。

行为：

- 没有活动搜索时，新请求立即成为活动搜索。
- 已有活动搜索时，新请求只成为最新待处理请求；同等待槽中的旧请求被替换。
- 活动搜索收到 `bestmove` 后才完成；随后启动最新待处理请求。
- 停止操作取消待处理请求，但活动会话仍保留到旧 `bestmove` 返回，以便正确识别并丢弃旧输出。
- 所有 `info`/`bestmove` 结果使用活动会话自己的会话号和 FEN，不使用收到输出时的全局当前盘面。

### 2. UciEngine 接入

`Analyze` 只提交会话请求。若已有活动搜索，发送 `stop`；待旧搜索结束后发送最新 `position fen` 和 `go`。

输出处理保持单线程顺序：先给结果绑定活动会话，再完成活动会话并启动待处理请求。`currmove` 行可以继续解析深度等诊断信息，但没有 PV 时不产生推荐结果。

引擎重启时清空会话状态，防止旧进程状态泄漏到新进程。

### 3. AnalysisManager 的旧结果闸门

`SubmitBoard` 保存当前盘面的完整 FEN。收到引擎结果时：

- 结果 FEN 必须与当前 FEN 完全一致才触发 `AnalysisReceived`。
- 不再用当前 FEN 覆盖结果 FEN。
- 旧结果被丢弃，因此不能进入 `MainController.TryCaptureExpectedBoard`，也不能覆盖主界面和悬浮层。

### 4. 回合与提示

`MainWindow` 提取统一的提示刷新方法，在分析结果和已确认盘面到达时都可调用：

- 对手回合且启用“仅在我方回合推荐”：显示等待对手。
- 我方回合但当前盘面尚无匹配分析：显示“正在思考...”而不是保留旧等待提示。
- 收到匹配当前 FEN 的分析后显示真实推荐。
- 状态栏在有新提交走法时显示走法和下一行棋方，便于用户确认是否已追上快速落子。

UI 不再把陈旧结果用于新盘面；中央旧结果闸门是第一道保护，UI 的 FEN 检查是第二道保护。

### 5. 思考时间设置

`AppSettings` 默认值调整为：

- `MaxDepth = 30`
- `MaxTimeMs = 4000`
- `MoveTime = 0`，避免旧的倍率配置绕过毫秒时间限制。

`AnalysisManager.SubmitBoard` 和 `AnalyzeNow` 统一使用 `MaxDepth`、`MaxNodes`、`MaxTimeMs`。当节点数为 0 时，不再通过 `MoveTime * 1000` 替代时间限制。

主界面增加“最长思考”下拉框，提供 1、2、4、6 秒，默认 4 秒；保存配置时写入 `MaxTimeMs`。已有用户配置保留其显式值，不强制覆盖。

## 异常与恢复

- 无法由合法走法解释的盘面继续保留已确认基准，不回退到整张候选盘面重锚定。
- 原始占用证据不足时仍拒绝提交，但状态说明保留，不静默翻回合。
- 旧搜索在停止期间产生的输出按旧 FEN 丢弃，不参与恢复。
- 新对局和首次建盘行为保持现有设计。

## 测试与验收

1. 搜索会话：首个请求立即启动；活动期间的多个请求只保留最新；旧 `bestmove` 完成后启动最新请求。
2. 结果归属：旧 FEN 的结果不会触发当前盘面的分析事件，也不会生成预期盘面。
3. 推荐解析：`currmove` 单独出现时不产生推荐；带 PV 的 `info` 正常产生推荐。
4. 真实截图：使用正确手动校准，从黑卒 `(2,5) -> (2,6)` 的前一盘面推导并安全提交，下一方为红方。
5. 现有 LogicTest 全部通过，包括不变子、两步追赶、高亮和 BGR/BGRA 等价测试。
6. Debug 与 Release 构建均为 0 错误。
7. 真实 JJ 对局由用户进行最终验证；若仍卡住，保留状态栏所显示的拒绝原因作为下一步诊断依据。
