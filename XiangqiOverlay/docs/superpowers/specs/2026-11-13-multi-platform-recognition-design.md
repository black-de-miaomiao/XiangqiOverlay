# 象棋多平台识别与“变子”修复设计

- 日期：2026-11-13
- 状态：已确认总体方向与盘面提交原则，细化设计由实现者决定
- 范围：JJ象棋、天天象棋、QQ/欢乐象棋，以及可扩展的通用 Windows 窗口识别

## 1. 背景与证据

当前项目已经具备窗口截图、棋盘校准、棋盘状态、FEN、象棋走法规则、Pikafish 分析和悬浮层显示能力，但视觉识别与状态提交耦合过重。

现有真实截图和回归程序输出表明：

1. 原始分类会把车、象、炮等棋子认错，开局锚定暂时掩盖了部分误识。
2. `PieceRecognizer` 同时承担颜色提取、分类、模板学习、高亮检测、走子继承、自愈和规则改写，职责过多。
3. `MainController` 的异常重锚定会把整张候选盘面提交为新基准；现有体检没有保证未移动棋子的兵种不变。
4. 用户提供的后一张问题截图明确显示“盘面连续异常已重新锚定”，同时游戏画面与软件小棋盘存在多处兵种不一致。
5. 生产截图为 BGRA 四通道，而现有离线测试主要使用 BGR 三通道，测试输入与实际运行路径不完全一致。

因此，本设计不是简单提高某个匹配阈值，也不是重写整个应用，而是保留可复用核心，重做视觉识别边界和盘面提交机制。

## 2. 目标

1. 修复正常对局中未移动棋子被自动改成其他兵种的问题，首先覆盖“炮变车”回归场景。
2. 提高 JJ象棋中局识别的稳定性，不再依赖规则把错误棋子强行改成另一兵种。
3. 建立平台化视觉架构，接入 JJ象棋、天天象棋、QQ/欢乐象棋。
4. 为其他中国象棋 Windows 窗口保留通用识别和手动校准入口。
5. 建立可重复运行的离线截图回归测试，使平台识别效果可以量化比较。

## 3. 非目标与边界

1. 不重写 Pikafish 通信、FEN、悬浮层和通用棋盘坐标系统。
2. 不在本期训练 ONNX/OCR 模型；未来可在相同分类接口后增加模型实现。
3. 不新增内存读取、自动点击或自动落子功能。
4. 不承诺在没有样本的情况下识别任意象棋界面。“通用支持”指可接入、可手动校准和可扩展，不等于所有平台零配置必识别。
5. 第一阶段仅支持 Windows 上可截取客户区的可见窗口，包括可正常截图的模拟器窗口；不直接连接手机。

## 4. 总体架构

保留以下组件：

- `ScreenCapturer`：窗口截图，但输出统一规范化。
- `BoardCalibration`：四角校准、双线性坐标映射、翻转和缩放。
- `BoardState`、`ChessMove`、`XiangqiMoveRules`：已确认盘面与规则。
- `AnalysisManager`、`UciEngine`：Pikafish 分析。
- 悬浮层和 WPF 小棋盘：继续使用已确认盘面。

新增或拆分以下职责：

### 4.1 平台注册与配置

`PlatformRegistry` 管理以下内置配置：

- `jj`：JJ象棋。
- `tiantian`：天天象棋。
- `qq-huanle`：QQ/欢乐象棋。
- `generic`：通用红黑中文棋子模式。

平台配置包含：

- 平台标识和显示名称。
- 可选窗口标题/进程提示。
- 棋盘自动检测参数；检测失败时使用现有手动四角校准。
- 棋子颜色与字心提取参数。
- 字模/贴图模板集合。
- 走子高亮检测配置；没有可靠高亮配置时禁用该辅助信息。

平台可由用户手动选择。自动识别只在对局未开始或停止状态下进行；开始追踪后锁定平台，不允许因单帧分类分数变化而中途切换。

### 4.2 原始观察模型

新增与 `BoardState` 分离的原始观察模型：

- `BoardObservation`：90 格观察结果、高亮格、平台、时间戳和整帧有效性。
- `CellObservation`：占用状态、颜色、候选兵种、分类置信度、第一/第二名分差和必要的诊断信息。

候选兵种允许为“未知”。占用和颜色可信、兵种不可信时，不再强行填入一个兵种，也不再借用 `Empty` 同时表示空格与未知兵种。

视觉层只负责产生观察结果，不修改已确认盘面。

### 4.3 平台化识别器

`VisionBoardReader` 改为组合式流水线：

1. 截图规范化。
2. 棋盘定位或使用手动校准。
3. 按平台配置提取棋子占用、颜色和字心。
4. 使用平台模板与通用后备分类器产生候选兵种和置信度。
5. 按平台配置检测高亮。
6. 输出 `BoardObservation`。

不为每个平台复制完整识别器。平台差异通过配置、模板集合及少量可替换策略实现。

### 4.4 盘面追踪与提交

新增独立的盘面追踪/提交组件，接管目前散落在 `PieceRecognizer` 和 `MainController` 中的状态修改职责：

- 输入：上一已确认 `BoardState`、当前稳定 `BoardObservation`。
- 输出：无变化、可提交走法、需要继续观察、需要人工同步等明确结果。
- 只有该组件可以生成新的已确认盘面；`MainController` 只负责调度和发布。

## 5. 识别改进

### 5.1 输入一致性

所有截图进入识别器前统一转换为 BGR 三通道。离线 PNG/JPEG 样本也走同一规范化入口，并为同一图像的三通道与四通道版本增加等价性测试。

### 5.2 平台模板库

模板按平台组织，例如：

```text
runtime/
  vision/
    jj/
      profile.json
      templates/
    tiantian/
      profile.json
      templates/
    qq-huanle/
      profile.json
      templates/
```

模板来自真实平台棋子截图，保留必要的字体、缩放和正常/高亮外观变体。内置 Windows 渲染字体只作为 `generic` 后备，不再作为所有平台的主要依据。

模板匹配同时利用归一化字心和完整棋子外观，但输出必须包含置信度与分差。分数不足或候选过于接近时返回未知兵种。

### 5.3 学习边界

允许的运行时学习仅限：

- 完整开局中由标准位置唯一确定兵种的颜色匹配样本。
- 经人工确认或离线标注后加入的样本。

禁止把未确认的分类预测直接反哺为同类型新模板。运行时自适应样本只归属于当前锁定平台；平台模板包不被普通识别循环自动改写。

### 5.4 象棋规则的正确用途

象棋规则用于：

- 校验走法。
- 检查已确认盘面是否可提交给引擎。
- 标记观察结果中的矛盾。

象棋规则不再用于把“多余的车”改成兵、把过河象改成兵或把其他误识棋子降级为另一兵种。无效盘面应被拒绝或等待校正。

## 6. 防止“变子”的状态不变量

以下规则为强制约束：

1. **已确认棋子的兵种只能随合法走子移动，不能在同一格自动变成另一兵种。**
2. 普通走子、吃子和连续两步追赶必须从上一已确认盘面执行 `ApplyMove`，不能直接提交整张视觉候选盘面。
3. 未移动且颜色未变的格子必须继承上一已确认兵种。
4. 单纯的单格兵种变化不得触发自动“自愈”并进入已确认盘面。
5. 异常重锚定不得顺带修改无走子证据格子的兵种。
6. 只有初始建盘、新对局或明确的人工校正可以建立/更改棋子类型真值。
7. 引擎预期盘面只能作为合法走法候选，仍需与当前稳定的占用和颜色观察相符。

## 7. 各场景处理

### 7.1 开局与新对局

完整初始阵列可以继续使用位置真值建立标准开局。新对局确认后重置行棋方、追踪状态和当前平台的临时自适应数据，但不自动切换平台。

### 7.2 中局首次启动

使用当前平台模板进行稳定多帧识别。只有棋子类型置信度达到门槛且整盘有效时才建立初始基准；存在关键低置信格子时提示用户重新校准或等待清晰画面，不猜测提交。

### 7.3 普通走子与吃子

根据占用和颜色变化生成候选走法，再按象棋规则过滤。提交时使用上一基准执行走法，避免无关格子的分类噪声进入新基准。

### 7.4 快速连续两步

保留两步合法走法搜索，但搜索目标只使用稳定的占用、颜色和可信高亮信息。最终盘面由两次 `ApplyMove` 生成，而不是直接采纳视觉类型。

### 7.5 高亮与动画

高亮只作为落点辅助证据，不单独证明棋子兵种。动画帧、低置信帧和整帧异常继续观察；平台没有可靠高亮规则时不启用高亮救援。

### 7.6 持续异常或漏掉多步

不再因异常持续固定帧数而接受整张候选盘面。优先尝试合法走法追赶；无法唯一解释时保留旧基准，显示明确的“需要重新同步”状态。用户可重新校准或执行受同样不变量约束的手动同步。

## 8. 错误处理与诊断

1. 低置信分类：保留占用/颜色观察，兵种标为未知，不进入模板学习。
2. 非法或无效盘面：不提交 Pikafish，状态栏给出可操作的提示。
3. 平台模板缺失：提示平台配置不完整，可退回通用模式，不静默套用其他平台模板。
4. 自动棋盘定位失败：继续使用手动四角校准。
5. 截图失败或为空：保留旧盘面并按现有节奏重试。
6. `EnableDebugLog` 启用后记录平台、原始/已确认 FEN、差异格、走法、提交原因和拒绝原因；默认不保存完整截图，避免无关窗口内容被持久化。

## 9. 测试设计

### 9.1 “炮变车”强制回归

建立确定的逻辑复现：已确认盘面中红炮保持不动，原始观察连续把该格报为高置信红车，同时其他格产生变化并触发旧实现的重锚定条件。

验收：无论经过单步提交、连续两步追赶或异常处理，已确认盘面中的该棋子始终保持为炮；无关格子的类型也不得改变。

### 9.2 状态不变量测试

覆盖：

- 普通移动和吃子只改变走子相关格。
- 连续两步只改变两步相关格。
- 单格类型抖动不修改已确认盘面。
- 高亮不会把无走子证据的棋子改成其他兵种。
- 持续异常不会自动提交整张误识盘面。
- 新对局和初始建盘仍可正确建立类型真值。

### 9.3 图像回归样本

用户提供的两张 JJ 问题截图作为诊断样本，裁剪出真实游戏区域，不使用其中的软件小棋盘作为识别输入。另使用合成状态序列验证提交不变量，避免把两张不同局面误当作严格的逐帧前后样本。

天天象棋与 QQ/欢乐象棋在实际接入前分别收集：

- 完整开局。
- 中局。
- 走子后高亮/无高亮画面。
- 红方在下与红方在上。
- 至少一种不同窗口尺寸。

每个样本保存人工确认的期望盘面或关键棋子断言。没有真实样本和期望结果的平台不得宣称识别验证通过。

### 9.4 兼容性与构建验证

- 同一图像的 BGR/BGRA 输入产生一致观察。
- 现有有效规则、校准、FEN 和引擎测试继续通过。
- 原先专门验证“自动自愈会改变兵种”或“规则会降级兵种”的测试由新的不变量测试替代。
- `LogicTest` 全部通过。
- `XiangqiOverlay.sln` Debug 与 Release 构建通过。

## 10. 实施顺序

1. 先写失败的状态回归，复现重锚定/走子提交导致无关棋子变种。
2. 分离原始观察与已确认盘面，收紧所有提交入口，先让 JJ 不再变子。
3. 统一截图输入并拆分平台识别接口，迁移 JJ 的真实模板与参数。
4. 建立离线样本目录和诊断输出，量化 JJ 原始识别准确率。
5. 根据真实样本接入天天象棋，完成该平台回归。
6. 根据真实样本接入 QQ/欢乐象棋，完成该平台回归。
7. 保留通用模式、手动校准和后续平台扩展文档。

每个阶段独立验证，不用“增加平台”同时掩盖或改变“变子”修复的测试结果。

## 11. 完成标准

1. 用户指出的炮在正常对局中不会再因自动自愈、走子提交或重锚定变成车。
2. 任一已确认盘面的无关格子不会因另一处走子被改写兵种。
3. JJ象棋的原始识别结果有离线样本验证，不再只验证开局锚定后的正确外观。
4. JJ、天天象棋、QQ/欢乐象棋均有独立平台配置；后两者只有在真实样本测试通过后才标记为已验证支持。
5. 新平台可以通过配置和模板接入，无需复制修改整套状态追踪和引擎代码。
6. 无法可靠识别时，程序明确等待或请求校正，而不是猜测并污染整局基准。
